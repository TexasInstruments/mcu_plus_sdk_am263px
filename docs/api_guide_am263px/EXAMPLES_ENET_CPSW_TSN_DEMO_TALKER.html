Introduction

This example is the talker (measurement) side of a two-image TSN demo: tsn_demo_talker and Enet CPSW TSN Integrated Demo - Listener. It configures and tests end-to-end latency for real-time and background traffic. The setup combines various TSN standards, including gPTP 802.1AS, scheduled traffic 802.1Qbv, frame preemption 802.3br, and cut-through switching.

It generates periodic "time-critical" probe stream shares the wire with a saturating "bulk" background stream, across a chain of boards. Without any TSN features turned on, a bulk frame that's already in flight can delay a probe that arrives right behind it - and that risk compounds at every hop in the chain. Enabling TSN features eliminates this cumulative delay, drastically reducing end-to-end latency and ensuring deterministic delivery for high-priority traffic.

Roles:

  • Talker (this example) is the gPTP grandmaster for the chain. It acts as traffic generator by generating express probe stream and bulk background stream. It also computes/reports all latency statistics for the echoed probe stream.
  • Every other board runs the listener image (Enet CPSW TSN Integrated Demo - Listener). A listener acts as GPTP slave and it forwards transit traffic in CPSW hardware (the ALE) without ever involving its CPU, and echoes the probe addressed to it back to the talker with two extra timestamps embedded in the payload.

Talker and Listener demo examples replicates actual industrial and automotive deployments, such as daisy-chained I/O modules, serial robotic cells, or in-vehicle backbone segments. Mirroring these topologies allows developers to observe how TSN performance benefits compound across network hops under realistic conditions.

This example does the following:

  • Target-side application running on a Cortex R5F core.
  • CPSW in switch mode, both MAC ports enabled, gPTP grandmaster.
  • Generates a periodic "express" probe frame and, optionally, a saturating "bulk" background stream of its own, each on its own DMA channel.
  • Applies/toggles EST, IET (frame preemption) and cut-through from a UART menu while running - live, not just at boot.
  • Times every express probe round-trip (talker TX -> listener echo -> talker RX) using CPTS hardware timestamps, and reports latency distribution, jitter and loss statistics per run, plus a side-by-side TSN-off-vs-TSN-on comparison.
Note
IET (frame preemption) and cut-through are only available on AM261x CPSW - see the feature table below. On any other supported SoC, the console menu simply won't offer the ‘'i’/'u'` toggles at all, rather than accepting them and silently doing nothing.

TSN features showcased

Feature Standard Functional Description Demonstration Impact
gPTP IEEE 802.1AS Synchronizes a highly accurate, shared time base across all network nodes in the chain. Core Foundation: Validates live synchronization status; accurate latency measurement reporting depends entirely on this unified clock.
EST (Scheduled Traffic) IEEE 802.1Qbv Time-gates egress queues to reserve dedicated, isolated transmission windows for time-critical data. Jitter Elimination: Guarantees express traffic a low-jitter, bounded delivery path even during periods of maximum background stream saturation.
IET (Frame Preemption) IEEE 802.3br Allows an express frame to instantly interrupt an active, low-priority frame mid-transmission. Delay Reduction: Minimizes worst-case blockages from background traffic, which significantly narrows the required EST guard bands.
Cut-Through Switching — Starts forwarding packet headers immediately upon reception rather than waiting to store the full frame. Hop Optimization: Substantially decreases the per-hop latency overhead, a performance benefit that multiplies with the length of the chain.

Chain topology - EVM Connections

Each board has exactly two CPSW MAC ports, which makes a line (daisy-chain) topology the natural fit - one port faces "up" the chain, the other faces "down" toward the next node:

Talker,Listener EVM Connections
  • The talker's MAC port 1 is where an external PC (or another traffic generator) can inject a saturating background load - this is optional, and covered in more detail below.
  • The talker's MAC port 2 goes to Listener 1's MAC port 1.
  • Listener 1's MAC port 2 goes to Listener 2's MAC port 1, and so on down the chain; the last listener's second port is left unconnected in daisy chain.

Contention with Background traffic

By default, the talker doesn't generate any bulk traffic of its own - the contended run modes (‘'2’/'3'` below) expect the background load to come from an external PC connected to the talker's MAC port 1. Anything the PC sends that isn't tagged with the express or gPTP priority lands in the demo's "open" EST window exactly like a bulk stream would, so no special frame format is required on the PC side - see the wire traffic table below for the priorities to avoid.

If PC is not connected to talker, then user can generate a 300Mbps bulk stream of its own in software instead - this is a build-time option (TSNDEMO_ENABLE_BULK_TASK in tsndemo_talker.c, off by default), not a console toggle.

Bidirectional, chain-position-staggered EST

A single, identical EST gate schedule is not valid for every port on every node in a multi-hop chain, so this demo computes a different schedule per port based on that node's position:

  • Downstream ports (facing away from the talker): the express gate window keeps a fixed width, but starts later by one hop-increment per hop - accounting for the real, accumulating time a forward express frame takes to reach each successive node.
  • Upstream ports (facing back toward the talker, i.e. the echo path): the express gate window both starts later and grows wider the further back a node is from the chain's far end - the software-driven echo turnaround has its own, larger latency floor, and the timing uncertainty of exactly when an echo left a downstream hop's window accumulates hop-by-hop on the way back.
  • The per-hop increment is derived based on TSN features enabled: it collapses to a small, near-constant value when IET or cut-through is active on that hop, or scales with the configured bulk frame size when neither is active (a large in-flight bulk frame can block an express frame from even reaching its egress queue without cut-through/preemption).

Wire traffic composition

Traffic EtherType Priority (PCP) Typical size Pattern
gPTP 0x88F7 7 (always-open gate) small, per the 802.1AS profile Periodic (Sync/Announce/Pdelay)
Express probe 0x88B5 5 (protected EST window) 256 bytes Fixed 125 µs period
Bulk / background load 0x88B6 (talker's own generator) or whatever a PC sends 1 (open window only) 1450 bytes (talker's own generator); PC traffic can be anything Back-to-back, not periodic

If you're driving bulk traffic from an external PC and want it to behave like the talker's own bulk stream, the only real requirement is: don't tag it with PCP 5 or PCP 7.

TSN feature configuration

This section is the "how do I actually change this" reference - what each console key does, and which source file to edit if the console toggle isn't enough.

EST (‘'e’`)

Toggling ‘'e’` computes and applies a fresh admin list on every MAC port, using the chain-position-staggered scheme described above, then enables the TAS state machine. Press it again to disable EST (falls back to open gating on every port).

EST schedule parameters
Parameter Value
BaseTime Current gPTP time + TSNDEMO_EST_BASETIME_MARGIN_NS (2 sec), rounded up to the next CycleTime boundary, then offset per-port by this port's chain-position stagger (0 for the talker, which is always downstream and unstaggered)
CycleTime TSNDEMO_EST_CYCLE_NS = 125000 ns (125 usec), fixed
Gate control list (3 entries per port, every cycle) - values shown for the talker's port (downstream, fixed width) with IET off
Gate Control Time Interval Traffic Allowed
oCoCCCCC 20000 ns gPTP (pri7) + express probe (pri5, TSNDEMO_PCP_EXPRESS)
oooooooo 92500 ns Everything - bulk (pri1, TSNDEMO_PCP_BULK), gPTP, and any other priority not explicitly protected
oCCCCCCC 12500 ns gPTP only (guard band ahead of next cycle's express window)

Gate bits are ordered pri7..pri0 (o = open, C = closed).

  • These numbers hold for the talker's port and every listener's downstream-facing port, where the express window is fixed at TSNDEMO_EST_DOWNSTREAM_WIDTH_NS = 20000 ns. A listener's upstream/echo-facing port opens a wider express window instead - see Enet CPSW TSN Integrated Demo - Listener's "EST schedule parameters" section for that case.
  • The 12500 ns guard band (TSNDEMO_EST_GUARD_EST_ONLY_NS) shown here is with IET off. Enabling IET shrinks the guard band to TSNDEMO_EST_GUARD_EST_IET_NS (1500 ns), which widens the everything-else window to 103500 ns.

If you want to change the schedule itself rather than just turning it on and off, everything is in tsndemo.h:

  • TSNDEMO_EST_CYCLE_NS - the EST cycle time (125 µs by default, chosen to match the express probe's own period exactly).
  • TSNDEMO_EST_DOWNSTREAM_WIDTH_NS - how wide the protected window is on a downstream port.
  • TSNDEMO_EST_ECHO_MIN_NS / TSNDEMO_EST_ECHO_MAX_NS - the software echo-turnaround latency floor/ceiling that sizes an upstream port's window.
  • TSNDEMO_EST_HOPINC_FAST_NS - the per-hop stagger increment used when IET or cut-through is active on that hop (when neither is active, the increment is computed instead, from the configured bulk frame size - see TsnDemoFeature_hopIncNs() in tsndemo_feature.c).

IET (‘'i’`)

Toggling 'i' enables frame preemption on every chain-facing port (and runs the verification handshake with the link partner - this is why listeners should have IET on before the talker, see the recommended script below). Express and preemptable priroity queues are configured in gTsnDemoIetCfg in tsndemo_feature.c:

Priority (PCP) Traffic in this demo Classification
7 gPTP Express (never preempted)
6 (unused) Express
5 Express probe Express
0-4 Bulk (uses PCP 1) Preemptable

Minimum non-final fragment size is 128 bytes (minFragSize = 1), and preemption verification is enabled (mac_verify_enable = true) - both ends of a link must have IET enabled for verification to succeed.

Cut-through (‘'u’`)

Priority (PCP) Cut-through enabled
0 - 7 (all) Yes (TSNDEMO_CUTTHRU_PRI_MASK = 0xFF)

By default this mask covers every priority, including bulk - a large in-flight bulk frame still fully occupies a hop before an express frame behind it can be relayed otherwise.

Steps to Run the Example

Build the example

  • When using CCS projects to build, import the CCS project for the required combination and build it using the CCS project menu (see Using SDK with CCS Projects).
  • When using makefiles to build, note the required combination and build using make command (see Using SDK with Makefiles)
  • When building via makefiles for a specific AM261x board variant, make sure the board's own TSNDEMO_BOARD_AM261X_LP / TSNDEMO_BOARD_AM261X_SOM macro is defined (already set correctly per-board by the shipped Makefiles) - it selects the correct CPTS tick rate for that board's silicon, which the gate-locked pacing described below depends on.

HW Setup

Note
Make sure you have setup the EVM with cable connections as shown here, EVM Setup. In addition do below steps.
  • Wire the chain as shown in the topology diagram above: this board's MAC port 2 goes to the first listener's MAC port 1.
  • Connect a PC to this board's MAC port 1 and start bulk traffic generator.
  • All links must run at 1 Gbit - the EST schedule's timing assumptions (section "Bidirectional, chain-position-staggered EST" above) are computed for 1 Gbit link speed.

Run the example

Attention
If you need to reload and run again, a CPU power-cycle is MUST
  • Launch a CCS debug session and run the example executable, see CCS Launch, Load and Run.
  • At the UART prompt, enter the total number of nodes in the chain (2..4, including this talker). The talker's own node id is always 0 and its downstream port is always fixed to MAC port 2 - only the total chain length is asked.
  • Wait for gPTP to reach sync-stable and for link speed to be checked; the menu below prints once both are done.

Recommended demo script:

  1. Enable the features you want to show on every listener first (e/i/u) - IET specifically needs the link partner's preemption enabled to complete its verification handshake, so listeners should be set before the talker.
  2. On the talker, press 2 - the contended run with TSN off. Let it complete.
  3. Press 3 - same contention, TSN features on.
  4. Press c - prints the side-by-side table: p99 one-way latency, PDV, max latency, loss %, and bulk throughput ("cost of TSN"), TSN-off vs TSN-on, with the improvement factor.

Field Meaning

PDV (p99 - min) Jitter headline - the number that matters most for control-loop determinism
loss % Probes that timed out with no echo
out-of-order / stale / ts-fail Diagnostic counters
bulk offered load (Mbit/s) How much background traffic was actually pushed during the window

Troubleshooting issues

  • Link not at 1 Gbit: the EST schedule's per-hop timing math assumes 1 Gbit links throughout the chain; a lower-speed link will make the express window mistimed relative to real transit time.
  • CPPI descriptor / MPU region sizing: the CPPI descriptor region must fit entirely inside a non-cacheable MPU region. Increasing DMA packet counts can grow the descriptor pool past that region's size (EnetCpdma_open then fails with "descriptors are not in un-cached memory region") - re-check the MPU region size if you change packet pool counts.
  • Wrong/missing board macro: if d reports pacing as "plain timer, NOT gate-locked" when EST is on and you expected GENF locking, check that the correct TSNDEMO_BOARD_AM261X_LP/_SOM macro is defined for your board - using the wrong one applies the wrong CPTS tick rate and the schedule will look correct in software but be wrong on the wire.
  • Round-trip report always shows "no samples": if tx/rx counts in the report look healthy (loss near 0%) but round-trip latency still shows no samples, hardware RX timestamping on the host port has somehow ended up disabled (enet_cpsw1.cptsHostRxTsEn in example.syscfg) - it needs to be true, since the round-trip measurement depends on a hardware RX timestamp of the returning echo.
