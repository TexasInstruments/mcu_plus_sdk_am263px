Layer 2 Latency

RX/TX Latency here is one-way, wire-to-application (or application-to-wire) latency, split into where it's spent: CPU<->CPSW is time inside the SoC (CPSW switch + CPDMA + interrupt/ISR handling up to/from the application buffer), and PHY is the fixed latency contributed by the DP83869HM PHY itself (from its datasheet, not measured on this setup). Total Latency is the sum of Phy delay and time taken by packet to/from CPU DMA Trigger to Mac.

UDP Throughput

Unlike the TCP table above, the Bandwidth column in the UDP RX rows is the offered load requested on the host PC (via iperf's -b <bw>, see the commands below) - not necessarily what the EVM actually received. Each of the 3 UDP RX rows is one offered-load step (5/10/15 Mbps for 64B datagrams, scaling up for larger datagrams); Packet Loss (%) at that row shows how much of that offered load the EVM failed to receive. UDP RX (Max) and UDP TX (Max) are the highest offered load (RX) or transmit rate (TX) the EVM could sustain at that datagram size while keeping packet loss low.

Analysis: Small datagrams (64B) are the worst case by far - sustainable throughput tops out around 5 Mbps with 81% CPU load, because per-packet software overhead (not link bandwidth) dominates at high packet rates for tiny payloads. Throughput scales up sharply with datagram size: max-size 1470B datagrams sustain 125 Mbps RX / 258 Mbps TX, since the same per-packet overhead is amortized over far more payload bytes. TX consistently out-sustains RX at every datagram size (e.g. 258 vs 125 Mbps at 1470B) for the same reason as TCP above - the receive path pays extra for buffer/queue management that the transmit path doesn't.

Host PC commands:

  • Test with datagram length of 64B:
    $iperf -c <evm_ip> -u -l64 -b <bw> -r
    where <bw> is 5M, 10M, 15M, etc
  • Test with datagram length of 256B:
    $iperf -c <evm_ip> -u -l256 -b <bw> -r
    where <bw> is 25M, 50M, 100M, etc
  • Test with datagram length of 512B:
    $iperf -c <evm_ip> -u -l512 -b <bw> -r
    where <bw> is 25M, 50M, 100M, etc
  • Test with datagram length of 1470B (max):
    $iperf -c <evm_ip> -u -b <bw> -r
    where <bw> is 25M, 50M, 100M, etc

Ether-Ring Performance

Redundancy-traffic latency in an Ether-Ring topology, measured for the three traffic profiles defined by Enet CPSW Ether-Ring Real-time and LWIP Traffic Generator Application (background LwIP traffic running concurrently in all three): Profile-A sends more than it receives (simulating a Zonal controller streaming to a central compute node), Profile-B is the inverse, and Profile-C sends/receives at the same rate.
